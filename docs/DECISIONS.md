# Architecture Decision Records

## ADR-001: Two classes only (person, forklift) for V1
Dropped PPE/pallet/rack classes despite collecting them. The risk model
consumes only person + forklift position and velocity — PPE never enters
the BEV raster. Partially-annotated extra classes would have hurt the
detector without adding downstream value. Deferred to V2.

## ADR-002: Class remapping by name, not index
Merge script maps source classes by name read from each data.yaml, not by
hardcoded index. An earlier index-based approach silently miscounted a
source's small_load_carrier (index 3) as person (index 3). Name-based
mapping makes adding new sources safe.

## ADR-003: BoT-SORT over ByteTrack
Warehouse workers wear near-identical hi-vis; motion-only tracking swaps
IDs when paths cross. An ID switch fabricates a false velocity vector,
producing a false conflict prediction downstream. BoT-SORT's appearance
embedding reduces this.

## ADR-004: Fixed cameras only
Homography is valid only for a single fixed viewpoint. Moving-camera footage
(handheld DVIDS clips) breaks metric projection and is excluded. Confirmed by
testing: moving-camera clips showed severe ID churn and box-edge clipping;
fixed-camera footage tracked cleanly.

## ADR-005: Perceptual-hash dedup before train/val/test split
Roboflow datasets are heavily re-forked; the same image appears across
sources. Deduplicating before splitting prevents the same scene landing in
both train and test, which would inflate reported mAP. Removed 8,767 dupes.

## ADR-006: TalTech videos lack floor pedestrians
The 5 fixed-camera TalTech videos contain only a seated forklift driver, no
pedestrians walking the floor. They validate detection, tracking, and
homography on real fixed-camera footage but cannot demonstrate a
forklift-pedestrian conflict. Conflict scenarios are therefore generated by
the procedural simulator (Phase 6) — also the correct approach since real
near-misses cannot be safely staged. Green aisle floor-lines serve as
homography calibration references.

## ADR-007: Tracking stability quantified across 5 fixed cameras
Measured ID stability on all 5 TalTech cameras (~1250 frames each):
  Cam1: 4 IDs, avg lifespan 137f
  Cam2: 2 IDs, avg lifespan 84f
  Cam4: 5 IDs, avg lifespan 90f
  Cam5: 5 IDs, avg lifespan 380f
  Cam3: 3 IDs, avg lifespan 8f (heavy rack occlusion, side-on angle)
4/5 cameras track stably. Primary homography/pipeline development uses
Camera1 and Camera5.

## ADR-008: Homography calibration on Camera1
Calibrated a pixel->metres homography using the 4 corners of the green aisle
floor-lines. Reprojection error 0 cm on calibration points; validated on a
real tracked forklift position which projected to (1.06 m, 9.74 m) — inside
aisle bounds, confirming the full detect->track->project chain. Aisle
dimensions (3.5 m x 11 m) estimated for the synthetic scene; absolute scale
approximate, relative distances consistent — sufficient for TTC/PET.

## ADR-009: Trajectory corpus assembly (Phase 4)
Fused tracking + homography into a metric trajectory corpus: per-frame
position (m), velocity (m/s), and speed for each track. Applied class-lock
(majority vote per track_id) to prevent mid-track class flips, and 5-frame
rolling-mean velocity smoothing to remove tracker jitter. Forklift speeds
(mean 0.66, max 5.0 m/s) fall in the expected warehouse range, validating
the metric scale. Camera1 yields forklift-only tracks (no floor pedestrians,
per ADR-006); pedestrian-forklift conflict trajectories come from the
Phase 6 simulator.

## ADR-010: TTC/PET as the labelling function (Phase 5)
Conflict labels are generated by physics, not hand annotation. Time-to-collision
(quadratic solve on relative position/velocity with agent radii: person 0.4 m,
forklift 1.5 m) and post-encroachment time are computed per timestep. This makes
labels objective, reproducible, and free — no manual conflict annotation. Unit-
tested on 5 known cases (head-on 4.05 s, diverging inf, parallel inf, overlapping
0.0 s, PET 2.0 s), all exact. Note: TTC labels the training data; it is never
called at inference — the CNN predicts from the raster alone.

## ADR-011: Procedural simulator for conflict scenarios (Phase 6)
Real forklift-pedestrian near-misses cannot be safely staged and are absent from
the fixed-camera footage (ADR-006). Conflicts are therefore generated by a NumPy
procedural simulator: agents on a 3.5x20 m aisle at 10 Hz with randomised
waypoints and realistic speeds. label_timestep gates on BOTH TTC AND distance —
an early TTC-only version over-fired IMMINENT at 50%; adding the distance gate
corrected the distribution to a realistic 28%. Generated 2000 scenarios (400,160
rows: SAFE 61% / IMMINENT 28% / CAUTION 11%). Autonomous-driving teams solve the
rare-positive problem the same way.

## ADR-012: 6-channel BEV velocity raster (Phase 7)
Each scene is rendered to a (6, 64, 64) tensor: channels [person occupancy,
forklift occupancy, person vx, person vy, forklift vx, forklift vy]. Velocity is
encoded as signed metres/second directly in the raster, so motion is spatial and
a CNN can read it. 160,000 scenes converted. The full uncompressed dataset is
15.7 GB, so it is regenerated/loaded only on Kaggle, never on the local Mac
(loading it locally exhausts memory). Compressed npz is gitignored — the tensors
are regenerable from the simulator.

## ADR-013: Track fragmentation deferred; stitching in the demo
YOLO detection dropout (not a tracker failure) causes one real agent to receive
multiple track IDs over time — proved by raising track_buffer 30->60 with no
effect. In the Streamlit video demo this is mitigated with lightweight track-
stitching: a new ID is merged into a recent same-class track whose last floor
position is within 2.5 m and 25 frames. Production fix (appearance-based re-ID,
e.g. BoxMOT/OSNet) is documented as future work, not implemented for V1.

## ADR-014: BRIN trained from scratch, lr=3e-4 + cosine (Phase 8)
BRIN (custom residual CNN, 491k params) is trained from scratch because the input
modality — signed velocity rasters — has no pretrained weights; ImageNet features
are meaningless on a metres-per-second channel. First run at lr=1e-3 was unstable
(per-class recall lurched between epochs). Fixed with lr=3e-4 + CosineAnnealingLR
+ class-weighted cross-entropy. Final: 92.7% val accuracy, per-class recall
SAFE 0.92 / CAUTION 0.91 / IMMINENT 0.93. Trained on Kaggle GPU (local Mac cannot
hold the dataset). Optuna was evaluated but hand-tuning proved sufficient.

## ADR-015: Baseline comparison as the headline result
BRIN is compared against the naive always-SAFE classifier: baseline scores 63.1%
accuracy but 0% IMMINENT recall (catches no collisions); BRIN scores 92.7%
accuracy and 93% IMMINENT recall. This proves (a) accuracy is the wrong metric on
imbalanced safety data, and (b) the learned network captures conflict structure a
trivial model cannot. The 93-vs-0 gap is the core justification for the model.

## ADR-016: Grad-CAM for explainability (Phase 9)
Grad-CAM hooks on model.res3.conv2. On an IMMINENT scene the heatmap concentrates
on both agents and the corridor between them — the collision zone — confirming
BRIN attends to the real interaction rather than a dataset shortcut. Because the
input is a bird's-eye view in metric floor space, the explanation overlays
directly onto the floor, making it actionable rather than a blurry blob on a
camera image.
